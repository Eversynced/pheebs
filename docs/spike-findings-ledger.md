# Pheebs Spike Findings

**Append-only source of truth for what we have *empirically verified* about hook/event
payloads and agent behavior — especially where a vendor's docs (or a reasonable assumption)
say one thing and the real event data says another.**

Vendor hook docs are young and drift; our own assumptions about "surely field X is in the
payload" are often wrong. Rather than re-discover the same thing every spike, we record it
here once. **Before trusting a doc — or the absence of a field — for any payload assumption,
check this file first.** If it isn't here, verify it, then add it.

## When to add an entry

Add an entry whenever a spike (or incidental discovery) confirms, contradicts, or refines what
we believed about:

- which fields a specific hook payload actually carries (and their names/shapes),
- whether a hook fires at all, and under what conditions,
- any divergence between a tool's documentation and its real behavior,
- a limitation that caps what we can measure.

If the finding changes what a practice's detector can claim, also update
[`ai-proficiency-model-practice-and-signal-registry.md`](./ai-proficiency-model-practice-and-signal-registry.md)
and cite this ledger. If it changes what we capture, update [`architecture.md`](./architecture.md) too.

## Entry template

```
### YYYY-MM-DD — <one-line finding> [Status: CONFIRMED | UNVERIFIED | REFUTED]

- **Tool(s):** claude_code | cursor | codex
- **Hook / event:** <hook key(s) and pheebs event(s)>
- **Claim (doc/assumption):** what we believed or what the docs said
- **Finding:** what the real payload/behavior actually showed
- **Method:** how it was verified (e.g. PHEEBS_DEBUG dump; `codex exec --dangerously-bypass-hook-trust` + tee)
- **Impact:** schema change / detector claim changed / capped-by-tool / none
- **Ref:** PR (optional)
```

Keep entries short and factual. Never paste real prompt text, source, or file paths into a
finding — describe the *shape* (field names, presence, types), consistent with Pheebs's
privacy line.

### 2026-09-17 — Prometheus rendering adds unit and `_total` suffixes to the OTel metric names, so they are not what the Claude Code docs name them [Status: CONFIRMED]

- **Tool(s):** claude_code
- **Hook / event:** none (OTel metrics export)
- **Claim (doc/assumption):** the exporter's metric is `claude_code.token.usage`, so a query would name it that way.
- **Finding:** the Prometheus-rendered names carry dots as underscores plus a unit and an accumulation suffix: `claude_code_token_usage_tokens_total`, `claude_code_lines_of_code_count_total`, `claude_code_cost_usage_USD_total`, `claude_code_session_count_total`, `claude_code_active_time_seconds_total`, `claude_code_code_edit_tool_decision_total`, `claude_code_commit_count_total`, `claude_code_pull_request_count_total`. Note the capitalized `USD` in the cost metric. Eight metrics in total, which is the whole `claude_code_` surface present.
- **Method:** metric-name listing against the observability backend over a 30-day window.
- **Impact:** the consolidation job must query the rendered names; a query written from the docs matches nothing.

### 2026-09-17 — The `session_id` join holds between the token metric and the event table, and coverage is partial by install rather than by key [Status: CONFIRMED]

- **Tool(s):** claude_code
- **Hook / event:** `claude_code_token_usage_tokens_total` (OTel) joined to `events.session_id` (backend)
- **Claim (doc/assumption):** the join on `session.id` is verified on `lines_of_code.count` but not on `token.usage`, and might not hold there, in which case the consolidation job has no session key.
- **Finding:** it holds. The label is present and rendered `session_id` (underscore, not dot), and both sides carry the same 36-character UUID. Matched over one 12-hour window (2026-09-15 12:00 to 24:00 UTC): both sides carried comparable session counts, and well under half matched exactly. The full label set on the metric is `agent_name`, `claude_deployment_mode`, `effort`, `host_arch`, `instance`, `job`, `marketplace_name`, `mcp_server_name`, `mcp_tool_name`, `model`, `organization_id`, `os_type`, `os_version`, `plugin_name`, `process_owner`, `query_source`, `service_instance_id`, `service_name`, `service_version`, `session_id`, `skill_name`, `terminal_type`, `type`, `user_account_id`, `user_account_uuid`, `user_email`, `user_id`.
- **The part that matters as much as the join:** coverage is partial and uneven, and the reason is the install rather than the key. Per install in that window, the share of event-table sessions that also appear on the metric ranged from none at all to about two thirds. An install at zero has hooks and no OTel export, which is the same shape as a machine whose agent settings carry no `OTEL_` env block. In the other direction, most metric sessions have no event row at all, which is an install exporting OTel without pheebs hooks. Some of the gap on both sides is window-edge noise, but an install exporting nothing at all is not.
- **Method:** instant queries against the observability backend; SQL against the backend event table over the same window; set intersection on `session_id`, then broken down by install.
- **Impact:** the consolidation job keeps its key. It must treat an unmatched session as ordinary rather than as an error, and any per-session cost figure covers only the sessions where both halves are installed. That coverage is worth reporting as a number rather than assumed, and it is a deployment problem to fix, not a schema one.

### 2026-09-17 — `session_started` repeats for the same `session_id` on resume, and the model can change between them [Status: CONFIRMED]

- **Tool(s):** claude_code
- **Hook / event:** `SessionStart` → `session_started`
- **Claim (doc/assumption):** a `session_id` gets one `session_started`, so the event can stand for session creation.
- **Finding:** it repeats. Over 21 events on 18 distinct session ids, two ids carried more than one: one twice, one three times. The repeats arrive with `start_source: "resume"` (`"clear"` also appears in the wider set) and hours apart, up to a day later. In both cases the later record is a real continuation rather than a duplicate, and in one of them the `model` differs between the first record and the resume (`claude-sonnet-5` at startup, `claude-opus-5[1m]` on both resumes), so a session is not one model.
- **Method:** tally over the local JSONL event log, pheebs 0.17.0.
- **Impact:** counting `session_started` as a session double-counts a resumed one; `start_source` is the field that separates them. Per-session model attribution cannot assume a single model, which matters to any cost figure summed per session.

### 2026-09-17 — The `model` value is an alias, sometimes with a context suffix, and only sometimes a dated id [Status: CONFIRMED]

- **Tool(s):** claude_code
- **Hook / event:** `session_started.model` and the OTel `model` label
- **Claim (doc/assumption):** the model arrives as a full API id.
- **Finding:** three shapes appear on the OTel label, side by side: a bare alias (`claude-opus-5`, `claude-sonnet-5`, `claude-fable-5-1`), an alias with a context-window suffix in square brackets (`claude-opus-5[1m]`, `claude-fable-5[1m]`, `claude-opus-4-8[1m]`), and a full dated id (`claude-haiku-4-5-20251001`). The hook payload's `session_started.model` uses the same alias and suffixed-alias forms, so the two sides agree in shape. The `type` label alongside it takes `input`, `output`, `cacheRead` and `cacheCreation`, which is four series per session and model.
- **Method:** grouped instant query against the observability backend; tally over the local JSONL event log.
- **Impact:** a price or class table keyed on a dated API id will miss most rows. Whatever `model_classes` and `model_prices` key on has to normalize the suffix and resolve aliases, and it has to survive an id it has never seen.

### 2026-09-17 — Active series per session is around 20, which leaves the 150,000 ceiling far away [Status: CONFIRMED, at low session volume]

- **Tool(s):** claude_code
- **Hook / event:** all `claude_code_*` metrics
- **Claim (doc/assumption):** `session_id` rides on every series, so the cardinality might not scale past a handful of developers.
- **Finding:** on 2026-09-17 the whole `claude_code_*` surface held **245 active series over 12 live sessions**: 1 to 42 series per session, averaging about 20. Against a 150,000 active-series ceiling that is roughly 3,500 concurrent sessions at the worst per-session figure and about 7,500 at the average. The ceiling counts *active* series, so it bounds concurrent sessions rather than cumulative ones: a finished session's series go stale and stop counting.
- **Method:** instant queries (`count({__name__=~"claude_code_.+"})`, `count by (session_id) (...)`, `count(count by (user_id) (...))`) against the observability backend.
- **Impact:** cardinality is not a blocker at this size, and the figure is worth re-measuring once the developer count grows, since it scales with concurrency rather than with headcount.

### 2026-09-11 — Cursor's hook sees a real command's **name**, before expansion; Codex emits no `command_name` for a real skill [Status: CONFIRMED on both, for real invocations]

- **Tool(s):** cursor, codex
- **Hook / event:** Cursor `beforeSubmitPrompt` and Codex `UserPromptSubmit`, both → `prompt_submitted`
- **Claim (doc/assumption):** `command_name` on Cursor and Codex identifies an invoked command, the way Claude Code's `command_expanded.command_name` does. Neither tool carries a structured command field, so the name is parsed from the leading `/token` of the raw prompt, which raised the question this entry was opened to answer: does a **real** command reach the hook as its literal name, or already expanded into a body whose first token is ordinary prose? Opened and closed the same day; the open version of this entry recorded only that a **non-existent** `/token` passes through verbatim on both tools, and was explicit that this settled nothing about a real one.
- **Finding — Cursor: the hook fires BEFORE expansion, which is the good answer.** A real user-defined command at `.cursor/commands/pheebsprobe.md` was invoked as `/pheebsprobe` in the GUI. The captured `beforeSubmitPrompt.prompt` was the literal `/pheebsprobe`, **12 characters**, not the command body. Two controls fired in the same turn, so this is controlled rather than inferred: the model's reply carried the command-body marker `PHEEBSPROBE-EXPANDED-BODY-REACHED-THE-MODEL`, proving the command really executed and its body reached the model, and it also carried `RULE-WAS-IN-SCOPE`, confirming the `alwaysApply` rule was loaded in that same turn. **So Cursor expands the body for the model while the hook still sees the name.** Real Cursor commands are visible to the detector, and the worst case, a detector that captures only false positives, is **refuted** for Cursor.
- **Finding — Codex: the opposite, and worse.** On the **TUI**, an unrecognized `/token` is **rejected client-side** by the composer and never submitted, so the hook does **not** fire at all; the `codex exec` passthrough, where a non-existent `/pheebsprobe` did reach the hook verbatim, does **not** reproduce on the TUI. And a **real skill is not slash-invoked on this build**: skills are catalogued to the model and `/` covers built-ins only, so a genuine skill run arrives with an ordinary prose first token and yields **no** `command_name`. The marker control fired here too, so "the prompt looked like prose" is not confounded with "the skill never ran". **Net: a real Codex skill invocation can never produce `command_name` on either surface** — the TUI gives no signal at all (real invisible, phantom blocked) and `codex exec` gives false positives only (real invisible, phantom registers).
- **Method:** Cursor GUI session with a staged probe command and an `alwaysApply` rule, both markers read from the model's reply. Codex TUI, codex-cli **0.154.0**, isolated `CODEX_HOME`, capture hook on `UserPromptSubmit`, with a real project-local skill at `.agents/skills/<name>/SKILL.md` whose body emits a marker. Only field names, marker tokens and a prompt **length** were inspected; no prompt body and no path values are recorded here. **Version caveat:** that Codex hook payload carries **no version field** (keys observed: `cwd`, `hook_event_name`, `model`, `permission_mode`, `prompt`, `session_id`, `transcript_path`, `turn_id`), so the pin rests on `--version` agreeing with the TUI banner rather than on the payload. Given that `--version` drifted twice on 2026-09-11, treat it as the weaker of the two kinds of pin this file uses.
- **Scope limit:** on Codex, **skills** were driven. No user-definable, slash-invoked command mechanism was found in 0.154.0, so if such a mechanism exists the literal-versus-expanded question is untested for it.
- **Impact:** AR2 and AR3 stay 🟡 on **Cursor**, now for the two defects that survive this result rather than for an open worst case: no prompt event at all outside the GUI, and no auto-invoke path. On **Codex** both cells move to `n/a, not observable`, because a real invocation can never be captured and what `codex exec` does emit is only phantoms. TS1 inherits the Codex result. **No extractor change is available**, since the structured field does not exist to read, and an allowlist built from the `cursor_commands` / `codex_skills` scan results must **not** be built: it would couple the event layer to a scan result and bake our interpretation into emission. Filtering to commands that exist is a consumer's join.

### 2026-09-09 — Claude Code `PostModelSwitch` carries `from_model`/`to_model` and a `source` naming what caused the switch [Status: CONFIRMED for `source: command`; the rest of the `source` domain UNVERIFIED]

- **Tool(s):** claude_code
- **Hook / event:** `PostModelSwitch` → `model_switched` (and `PreModelSwitch`, observed but deliberately not registered)
- **Claim (doc/assumption):** the hook fires on a deliberate `/model` *and* on changes Claude Code makes for itself (an automatic fallback, a model restored on resume), which would make a restore indistinguishable from a human choice; and `from_model` might be absent or equal to `to_model` on the first switch of a resumed session.
- **Finding:** the payload carries `from_model` and `to_model` (both **resolved** model ids, e.g. `claude-opus-5[1m]` → `claude-sonnet-5`), `requested_model` (the alias as typed, e.g. `sonnet`, `null` for "default"), `source`, and a block of cache/cost advisory fields (`context_tokens`, `prompt_cache_warm`, `cache_ttl`, `estimated_cache_write_usd`, `pricing`) alongside the common `session_id` / `transcript_path` / `cwd` / `prompt_id`. **Provenance, because the two halves of this entry are not equally strong: the only `source` value ever seen in a captured payload here is `command`** (a `/model <name>`, the `/config` Model row, or fast mode promoting the model). The other four values — `picker`, `sdk`, `auto` (automatic fallback or other programmatic change) and `resume` (model restored while resuming a session) — and the restriction of `PreModelSwitch` to the first three are **read off the shipped 2.1.267 hook-input schema, not observed**. **No automatic fallback was driven at all**, so whether the hook fires on one, and with what `from_model`, is unestablished here; forcing one needs a rate limit or a model outage. On the schema's terms `source` is the field that separates a deliberate switch from an automatic one, and a consumer counting deliberate model choice filters to `command`/`picker`/`sdk` — but that filter rests on the vendor schema, not on anything this spike emitted. On **resume**: a `--continue` resume restored the session's model with **no `PostModelSwitch` at all** (the restore is silent on this version — the `resume` source value exists in the schema, so treat its absence as unobserved, not impossible), and the first deliberate switch *after* that resume carried a correct `from_model` — the restored model, not the user default, and not equal to `to_model`. Two further observations: `PreModelSwitch` fires on the *request*, ahead of a warm-cache confirmation gate that can still cancel it (observed: `Pre` fired, then `Post` only after the confirmation was accepted), which is why only `Post` is registered; and a resumed session's `SessionStart` payload carries **no `model` field**, so `session_started.model` is unset on resume and `model_switched` is the only in-band model signal such a session has.
- **Method:** live interactive `claude` (v2.1.267) driven through an Orca terminal, in a scratch directory carrying a project-local `SessionStart`/`PreModelSwitch`/`PostModelSwitch` capture hook appending raw stdin to JSONL — headless `claude -p` cannot issue `/model`. Four rounds: startup on the user default, `/model sonnet`, exit and `--continue` resume, `/model opus` in the resumed session. The `source` domains were read off the hook input schema in the shipped 2.1.267 bundle, which also names each value. Only field names, model ids and the coarse enum values were inspected; paths and prompt text were discarded.
- **Impact:** capture — `PostModelSwitch` is registered in `definitions.claude.ts` and `extractClaudeExtra` emits `from_model`, `to_model` and `switch_source` on `model_switched`; the advisory cache/cost fields are not captured (a cost estimate is a consumer's model, not a generic fact). Turns a session's model from a single value into a timeline, and gives MD1 a switch-level detector; the exclusion of `auto`/`resume` that detector performs is grounded in the vendor schema alone, since neither value was observed. Supersedes in part the 2026-07-07 entry below, which recorded that a mid-session switch fires no hook.
- **Standing risk:** the `source` domain is a vendor enum that may gain values; a consumer should treat any unrecognized value as *not* deliberate rather than defaulting it in. The `auto` path has never been driven, and the silent resume restore is a behaviour rather than a contract — re-verify both if a fallback or a resumed session ever starts reporting a switch.

- **Consequence (provenance):** invocation origin is derivable with no extra field. `event = 'command_expanded'` (also `expansion_type = 'slash_command'`) is user-explicit; `event = 'tool_use_completed' AND tool_name = 'Skill'` is agent/auto-invoke. A dedicated `invocation_source` field is unnecessary.
- **Method:** SQL over the live `events` table (per-session co-occurrence window; kit-slash vs Skill-tool totals per dev). Not yet sealed by a captured slash payload.
- **Impact:** none to schema; confirms the `command_name`-on-Skill change is non-duplicating. Watch for divergence if a future Claude Code version routes slash through the Skill tool.

### 2026-07-07 — Claude Code recurring hooks carry no `model` field [Status: CONFIRMED]

- **Tool(s):** claude_code
- **Hook / event:** `PostToolUse`, `Stop`, `UserPromptSubmit` (all recurring hooks) → `tool_use_completed`, `turn_ended`, `prompt_submitted`
- **Claim (doc/assumption):** the model could be read off a recurring payload to detect a
  mid-session `/model` switch.
- **Finding:** recurring payloads carry only `permission_mode`, `effort`, `prompt_id`,
  `session_id`, `transcript_path`, plus event-specific fields. **No `model` field (nor any
  alias).** `model` is emitted **only** on `session_started`, so a mid-session `/model` switch
  fires no hook and the session snapshot silently goes stale.
- **Method:** `PHEEBS_DEBUG` payload dump inspection across the recurring hooks.
- **Impact:** Models T2 capped 🟠 — per-event model capture is not possible via hooks; the only
  within-session model-variation signal is native OTel tokens-by-model (Claude Code + Codex),
  joined by session/developer. Scorecard "Models" Basis note already reflects this.
- **Superseded in part 2026-09-09** (see the `PostModelSwitch` entry above): the "fires no hook"
  half is **refuted** — a mid-session `/model` switch does fire `PostModelSwitch`, which carries
  `from_model`/`to_model`, so OTel tokens-by-model is no longer the only within-session signal.
  The original finding stands on its own terms: recurring payloads still carry no `model`, so the
  current model is still reconstructed from the `session_started` snapshot rather than read
  per-event.

### 2026-07 — MCP per-server identity is available on all three tools [Status: VERIFIED]

- **Tool(s):** cursor, claude_code, codex
- **Hook / event:** Cursor `afterMCPExecution` → `tool_use_completed`; Claude/Codex tool-use
  events (`tool_use_completed` / `tool_invoked`).
- **Claim (doc/assumption):** Cursor's tool name was believed to arrive as `MCP:<tool>` with **no
  per-server identity**, so distinct-MCP-server counting wasn't thought possible on Cursor (old
  basis for MCP T2 (cursor) 🟠).
- **Finding:** the Cursor `afterMCPExecution` payload **does** carry a dedicated `mcp_server_name`
  field alongside a bare `tool_name` (e.g. `tool_name: "list_directory"`,
  `mcp_server_name: "filesystem"`). Claude Code and Codex have no separate server field, but their
  MCP calls surface as a single `tool_name` following the `mcp__<server>__<method>` convention
  (e.g. `mcp__linear__list_issues`), from which the server segment is derivable (split on the first
  `__` after the `mcp__` prefix — server names may contain single underscores, e.g.
  `mcp__claude_ai_Google_Calendar__create_event` → `claude_ai_Google_Calendar`). The handler now
  normalizes all three onto one `mcp_server_name` field (`extractCursorExtra` reads it directly;
  `extractClaudeExtra` / `extractCodexExtra` derive it via `deriveMcpServerName`).
- **Method:** live Cursor `afterMCPExecution` payload capture (`PHEEBS_DEBUG`); Claude/Codex prefix
  convention is the documented `mcp__<server>__<method>` tool-name shape.
- **Impact:** MCP T2 moved 🟠 → 🟡 for Cursor, and the T2 evidence path is now the same
  `mcp_server_name` field on all three tools. "Across task types" still needs task
  semantics we don't capture, so the cell stays capped at 🟡.
